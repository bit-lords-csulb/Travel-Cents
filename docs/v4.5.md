# V4.5 — AI Chat Pipeline Fixes + Draft Trip Feature

**Branch:** `feature/new-chat-screen`
**Builds on:** `docs/v4.md` (phases 1–4 already merged; this doc scopes the remaining bugs and the draft trip feature)

---

## Context

The following issues were identified through manual testing of the current chat pipeline:

1. Starter cards inject false assumptions into the LLM via hidden `message` fields that differ from the visible label.
2. Destination recommendation cards appear deterministically after the first message, sourced from a hardcoded seed pool (`AiDestinationRecommendationEngine`), not from the LLM.
3. The fresh-chat session pre-populates destination cards before the user sends anything (`populateQuickIdeaSurfaces()`).
4. Tapping a destination card is a dead end — `selectDestinationRecommendation()` appends a hardcoded reply string and never calls `submitUserTurn()`, so no LLM response follows and the conversation stops.
5. The reply text after destination selection ("I can anchor the plan on X. Here are curated starter ideas...") is hardcoded and the promised starters never appear because `activeCuratedTripRow` is immediately cleared.

---

## Step 1 — Fix Starter Card Messages

**Files:** `data/ai/chat/AiChatCardCatalog.kt`

The `message` field on each `AiChatCardOption` is what actually gets sent to the LLM. Currently it expands the label with assumptions the user never expressed (e.g. "Romantic Trip" → "I want a romantic trip **for two**.", which introduces party size the user never stated).

- Set `message` equal to `label` for all starter cards, or rephrase as a neutral intent signal with no inferred specifics.
- "Romantic Trip" should send something like `"I want to plan a romantic trip."` — no party size, no implied traveler count.
- "Family Trip" → `"I want to plan a family trip."`
- Apply the same principle to all 6 starter options: the `message` should contain only what the label already communicates.

**Why this matters:** When two contradictory starter cards are selected (e.g. Romantic + Family), the LLM receives the two hidden messages and flags a contradiction the user never created. The fix eliminates fabricated context.

## Step 2 — Remove All Hardcoded Destination Recommendation Paths

**Files:** `ui/main/aichat/AiChatViewModel.kt`, `data/ai/chat/AiDestinationRecommendationEngine.kt`

### 2.1 Remove `populateQuickIdeaSurfaces()`
- Delete the `populateQuickIdeaSurfaces()` function from `AiChatViewModel`.
- Remove its call in `resetToFreshSession()`.
- The fresh-chat screen shows only the starter card landing. No destination rows are pre-populated.

### 2.2 Remove `AiDestinationRecommendationEngine` from post-message flow
In `resolveDestinationRecommendationRow()`, the current fallback path calls `AiDestinationRecommendationEngine.rankDestinations()` whenever `intakeResult` is null or `nextAction` is `SUGGEST_DESTINATIONS`. This produces the same static pool (Honolulu, Cancún, Bali, Tokyo, etc.) regardless of what the user said.

- Remove the fallback to `AiDestinationRecommendationEngine` from `resolveDestinationRecommendationRow()`.
- Destination cards now only appear when `intakeOrchestrator.suggestDestinations()` returns results — i.e. when the intake LLM explicitly decides destinations are ready to be suggested.
- If `suggestDestinations()` returns an empty list, no destination row is shown. The conversation continues with a follow-up question instead.
- `AiDestinationRecommendationEngine.kt` becomes unused and can be deleted along with `AiCuratedTripSeedCatalog.kt`.

### 2.3 Destination suggestion timing
The intake orchestrator system prompt already instructs the LLM not to suggest destinations until it has at least `trip_type`, 2 interests, and `budget_level`. Confirm this instruction is present and not overridden by any fallback path after this change.

## Step 3 — Fix Destination Selection to Route Through the LLM

**Files:** `ui/main/aichat/AiChatViewModel.kt`

### 3.1 Replace `selectDestinationRecommendation()` with a `submitUserTurn()` call
Currently `selectDestinationRecommendation()` manually builds a hardcoded assistant reply and updates session state without ever calling the LLM. Replace this:

- Compose a visible user message: `"Let's plan around {destination}"`.
- Compose an LLM user message that includes the destination and any match context from the recommendation.
- Pass both into `submitUserTurn()` exactly as any other user turn does.
- The LLM receives the full intake profile and conversation history, acknowledges the destination naturally, asks the next relevant follow-up question, or dispatches a tool call — same as any other turn.

### 3.2 Delete `buildDestinationRecommendationReply()`
This function and its two hardcoded template strings are no longer needed once 3.1 is in place.

### 3.3 Draft trip creation on confirmed destination
When the session state has a confirmed destination (either from a destination card tap or from the LLM's intake profile patch setting `destination`), create an `AiDraftTrip` in session state. See Step 4 for the full spec.

### 4.3 `AiChatItem.DraftTripCard`

In `buildVisibleItems()`, when `draftTrip != null`, append a `DraftTripCard` at the end of the list (after all text messages and active rows).

### 4.4 `AiDraftTripCard` composable

### 4.5 Pinned draft header bar

- Thumbnail of the hero image (circular, 40dp) + destination name + event count.
- Entire bar is tappable and scrolls the list back to the `DraftTripCard` item.
- Implemented in `AiTripChatPage.kt` using `LazyListState.firstVisibleItemIndex` to determine when the card has scrolled past the top.

### 4.6 Full draft trip view
Create `ui/main/aichat/AiDraftTripScreen.kt`:

- Full-screen overlay (shown via `AnimatedVisibility` slide-up from the bottom).
- Reuses `CurrentTripItineraryContent` and `CurrentTripHeader` directly — no new layout invented here.
- Top banner: "Draft — not saved yet" text + **Save to My Trips** button (prominent, primary color).
- Close/minimize button in the header collapses back to the card/pill.
- All existing interactions work as-is: event detail overlay (`CurrentTripEventDetailsDialog`), day view, calendar view.

### 4.7 Save to Firestore
In `AiChatViewModel`, add `saveDraftTrip()`:

- Builds an `Itinerary` from `draftTrip.intakeProfile` (destination, dates if known, etc.).
- Writes it to Firestore using `TripSyncRemoteDataSource`.
- Calls `TripSyncRemoteDataSource.upsertEvent()` for each event in `draftTrip.events`.
- On success: clears `draftTrip` from session state, emits a navigation event to open `CurrentTripScreen` with the new trip ID.
- On failure: shows an error in the draft view without losing the draft.

## Step 5 — LLM-Inferred Activities on Draft Creation

**Files:** `ui/main/aichat/AiChatViewModel.kt`, `data/ai/chat/AiToolRouterOrchestrator.kt`

When `createDraftTrip()` is called:

- Check `intakeProfile` for strong preference signals: specific activity mentions, restaurant requests, concert/event mentions, neighborhood preferences, cuisine preferences.
- If signals are present, immediately dispatch the appropriate tool call through `AiToolRouterOrchestrator` (same path as `dispatchToolCalls()` already uses): `SearchRestaurants`, `SearchActivities`, or `SearchEvents` with the confirmed destination as the city.
- Results appear as place recommendation row cards in the chat (existing `AiChatItem.PlaceRecommendationRow` path) — the user can add them to the draft from there.
- If no strong signals are present, the draft starts empty and the conversation continues naturally.

This keeps the draft creation lightweight: it is never pre-filled blindly, only when the user has already expressed intent.

## Step 7 — Image Caching for All Chat Images

**Files:** `ui/main/aichat/AiChatViewModel.kt`, `ui/main/aichat/components/AiDraftTripCard.kt`, `ui/main/aichat/components/AiRecommendationRow.kt`, `ui/main/aichat/components/AiCuratedTripRow.kt`

All images loaded in the AI chat — hero images, place recommendation card images, curated trip card images — must go through `ImageCacheManager` before being passed to Coil's `AsyncImage`. This prevents redundant network fetches on every scroll and session restore.

### 7.1 Cache key for chat images
Chat images are not tied to a Firestore trip document. Use the current chat `sessionId` as the `tripId` parameter in `ImageCacheManager`:

```kotlin
ImageCacheManager.resolveCachedMediaUrl(context, sessionId, remoteUrl)
```

`resolveCachedMediaUrl()` returns the local file path if already cached, otherwise the remote URL as a fallback — Coil handles both transparently.

### 7.2 Hero image caching (destination + curated trip cards)
In `launchHeroImageEnrichment()`, after `DestinationImageRepository.resolveDestinationImage()` returns a URL:
- Call `ImageCacheManager.cacheTripMedia(context, sessionId, listOf(resolvedUrl))` before storing the URL in `heroImageCache` and session state.
- Store the returned local path (if successful) instead of the remote URL in `draftTrip.heroImageUrl` and curated trip `heroImageUrl` fields.

### 7.3 Place recommendation image caching
In `AiPlaceRecommendationCoordinator` (or wherever recommendation images are resolved), after fetching Yelp/SerpAPI results that include image URLs:
- Batch-call `ImageCacheManager.cacheTripMedia(context, sessionId, imageUrls)` immediately after the fetch.
- Store the returned local paths alongside the recommendations before they are emitted into `activePlaceRecommendationRow`.

### 7.4 Session restore
When `restoreSnapshot()` is called, the session's `sessionId` is the same as when images were originally cached — `ImageCacheManager.localPathForUrl(context, sessionId, url)` will resolve correctly. No additional migration is needed.

### 7.5 Draft-to-saved trip image handoff
When `saveDraftTrip()` writes the trip to Firestore and gets back a real `tripId`:
- Call `ImageCacheManager.cacheTripMedia(context, newTripId, allImageUrls)` to copy cached assets under the new trip ID.
- This ensures the saved trip's `CurrentTripScreen` immediately shows images without a fresh network fetch.

### 7.6 Composable image loading
All `AsyncImage` calls in chat components must use `ImageCacheManager.resolveCachedMediaUrl()` to resolve the URL before passing it as the `model` parameter. Do not pass raw remote URLs directly to `AsyncImage` in any new chat component — always resolve through the cache first.
