# V5 — LLM-Guided Intake Stabilization Plan

**Builds on:** `docs/v4.5.md`

---

## Context

The desired behavior is:

- The LLM decides what information is still missing.
- The LLM chooses the next follow-up question.
- The LLM generates 2 to 6 context-appropriate answer cards.
- The UI renders a short acknowledgment, the question title, and tappable cards.
- Free text input remains available for custom answers.

The current failure mode is different from the earlier unsupported-model issue:

1. The latest intake call is reaching Groq with `response_format = {"type":"json_object"}` and `model = openai/gpt-oss-20b`.
2. Groq returns `400 json_validate_failed` after generation, which means the intake model output is not valid JSON for the requested turn.
3. `AiChatViewModel` then falls back to the general chat path, which is explicitly paragraph-oriented.
4. Because `intakeResult` is null on that path, no response card group is created and the user sees long prose instead of cards.

The goal of V5 is to keep the intake fully LLM-driven while making the structured response contract small enough to be reliable.

---

## Product Direction

This plan does **not** replace the intake flow with hardcoded questions.

The LLM should still decide:

- what is missing,
- what the next question should be,
- what options best fit the user's intent,
- how the structured intake profile should be patched.

What changes is the **shape of the output contract** and the **fallback behavior**:

- intake turns should return a very small JSON object,
- intake should never emit paragraph-style assistant prose,
- intake follow-ups should be cards-only,
- general chat fallback should not be allowed to invent the next intake question in prose.

---

## [x] Phase 1: Define a Minimal Intake Contract

**Goal:** Keep the LLM in control of the next question, but reduce the structured output to only what the UI needs.

**Files:** `data/ai/chat/AiTripIntakeOrchestrator.kt`, `data/ai/chat/AiTripIntakeSchema.kt`

- [x] Replace the current large intake response shape with a smaller, intake-specific contract.
- [x] Limit the intake response to fields required to:
  - patch the profile,
  - determine the next step,
  - render the acknowledgment,
  - render one follow-up card group.
- [x] Remove nonessential top-level fields from the prompt contract for intake turns, especially fields that do not affect immediate UI rendering.
- [x] Include an explicit JSON example in the intake prompt that matches the expected output exactly.
- [x] Keep the LLM responsible for generating:
  - `ack_key`,
  - `profile_patch`,
  - `next_action`,
  - `question_id`,
  - `question_title`,
  - `options`.

**Target shape**

```json
{
  "ack_key": "got_it",
  "profile_patch": {
    "trip_type": "romantic",
    "destination_style": ["beach"]
  },
  "next_action": "ask_more",
  "question_id": "destination_type",
  "question_title": "What kind of destination?",
  "options": [
    { "id": "tropical", "label": "Tropical", "message": "Tropical." },
    { "id": "coastal_town", "label": "Coastal town", "message": "A coastal town." },
    { "id": "beach_resort", "label": "Beach resort", "message": "A beach resort." }
  ]
}
```

**Why this matters:** the current intake prompt asks for too much structure, and the model is hitting a failure mode where the generated output is not valid JSON by the time Groq validates it.

## [ ] Phase 2: Make Intake Cards-Only

**Goal:** Ensure intake follow-ups always render as cards and never degrade into free-text follow-up prompts.

**Files:** `data/ai/chat/AiTripIntakeSchema.kt`, `data/ai/chat/AiTripIntakeOrchestrator.kt`

- [ ] Remove `TEXT` from `AiTripIntakeQuestionKind`.
- [ ] Remove the `AiTripIntakeQuestionKind.TEXT` branch from `assistantMessage`.
- [ ] Make cards the only valid intake follow-up mode when `next_action = ask_more`.
- [ ] Keep `question_kind = none` only for turns where no follow-up is needed.
- [ ] Update the intake prompt so the model is told to produce exactly one of:
  - no follow-up,
  - one cards follow-up.

**Why this matters:** even if the intake call succeeds, the remaining `TEXT` branch still allows runtime behavior that bypasses cards.

---

## [x] Phase 3: Simplify Assistant Rendering For Intake Turns

**Goal:** Make the assistant output on intake turns structurally short by design, not just by prompt suggestion.

**Files:** `data/ai/chat/AiTripIntakeSchema.kt`, `ui/main/aichat/AiChatViewModel.kt`

- [x] Restrict intake assistant copy to `ack_key + question_title` for card turns.
- [x] Do not allow intake turns to include paragraph descriptions, rationale, or inline option explanations.
- [x] Keep card labels short and UI-friendly.
- [x] Preserve the typed composer so users can always override the cards with custom input.

**Desired UX examples**

- `Got it! What kind of destination?`
- `Understood. What's your budget?`
- `Perfect. What pace sounds right?`

**Why this matters:** the UI should stay guided and concise even when the LLM is making the decisions.

---

## [ ] Phase 4: Replace Prose Fallback With Structured Retry

**Goal:** Prevent failed intake turns from dropping into the generic paragraph-chat path.

**Files:** `ui/main/aichat/AiChatViewModel.kt`, `data/ai/chat/AiTripIntakeOrchestrator.kt`

- [ ] When the intake call fails, do not immediately call the general chat completion path for that turn.
- [ ] Add one retry path that asks the intake model for an even smaller JSON object with the same semantics.
- [ ] Keep the retry focused on the minimum UI payload:
  - `ack_key`,
  - `next_action`,
  - `question_id`,
  - `question_title`,
  - `options`,
  - minimal `profile_patch`.
- [ ] If the retry also fails, return a neutral short failure message rather than a paragraph-style follow-up question.
- [ ] Only use the normal prose chat model for non-intake contexts where a paragraph answer is actually intended.

**Why this matters:** the current paragraph response is not a separate bug. It is the direct result of the app falling into the general chat fallback path.

---

## [x] Phase 5: Align Model Defaults And Runtime Configuration

**Goal:** Remove configuration drift between committed defaults and local overrides.

**Files:** `app/build.gradle.kts`, `data/ai/remote/LlmConfig.kt`

- [x] Set the checked-in default intake model to the actual model the intake path is expected to use.
- [x] Keep the chat model and intake model intentionally separate.
- [ ] Confirm that the chosen intake model is the one validated for this smaller JSON-object flow.
- [x] Remove reliance on `local.properties` as the only reason the app works correctly on one machine.

**Why this matters:** the current tree still defaults intake to `llama-3.3-70b-versatile`, which has already produced earlier structured-output failures when local overrides are absent.

## [ ] Phase 6: Add Better Intake Failure Observability

**Goal:** Make future intake failures diagnosable in one test run.

**Files:** `data/ai/remote/LlmClient.kt`, `ui/main/aichat/AiChatViewModel.kt`

- [ ] Log the intake request path distinctly from normal chat calls.
- [ ] Log the model name used for intake and for general chat.
- [ ] Log whether the intake path succeeded, retried, or fell back.
- [ ] On intake JSON parse failure, log the raw returned content in a safe truncated form for debug builds.
- [ ] Keep enough metadata to correlate on-device logs with Groq request IDs.

**Why this matters:** the last round of debugging was slowed by uncertainty over whether the app was still sending `json_schema` or had already moved to `json_object`.

## [ ] Phase 8: Manual QA Matrix

**Goal:** Validate that the LLM remains adaptive while the UI remains concise.

**Scenarios**

- [ ] `Romantic trip + Beach getaway`
  - Expected options should be beach-relevant, such as tropical, coastal town, beach resort.
- [ ] `Romantic trip + Nature escape`
  - Expected options should be nature-relevant, such as mountains, forest retreat, lakeside stay.
- [ ] `Family trip + Theme parks`
  - Expected options should be family-relevant and not romantic-coded.
- [ ] `Solo trip + Food-focused city`
  - Expected options should explore city type, cuisine focus, budget, or pace.
- [ ] Pure free-text custom answer after a card prompt
  - Expected behavior: intake profile updates and the next LLM-guided card question remains concise.

**Acceptance criteria**

- [ ] Intake turns render a short acknowledgment plus cards.
- [ ] The LLM chooses the next question based on user intent.
- [ ] Options fit the user's context and do not feel hardcoded.
- [ ] No long paragraph follow-up appears on intake turns.
- [ ] No Groq `json_validate_failed` errors occur in the validated happy path.

---

## Suggested Implementation Order

1. Phase 1 — minimal intake contract
2. Phase 2 — cards-only intake mode
3. Phase 3 — concise intake rendering
4. Phase 4 — structured retry instead of prose fallback
5. Phase 5 — model default cleanup
6. Phase 6 — observability
7. Phase 7 — tests
8. Phase 8 — manual QA

---

## Summary

V5 keeps the intake experience LLM-guided, but narrows the contract so the model only has to do one thing reliably on intake turns:

- infer what is missing,
- ask one short question,
- generate a small set of relevant options,
- return valid JSON the UI can render as cards.

That preserves the intelligence of the conversation while removing the main source of instability in the current pipeline.
