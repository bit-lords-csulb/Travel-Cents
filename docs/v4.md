# V4 — AI Chat Redesign: Full Phased Plan

**Branch:** `feature/new-chat-screen`
**Goal:** Make the AI chat screen the primary trip-planning surface with a compact schema-driven conversation flow, a simple default welcome screen, reusable current-trip and event UI, specialized handlers for new-trip intake, existing-trip edits, and social mentions, plus real place actions, a live draft trip view, and a home screen bookmarks widget backed by real data.

---

## Context & Architecture Notes

### How LLM context works (existing)
Every call to `LlmClient.complete()` already passes the full `llmHistory` list — every prior user and assistant turn — as part of the message array. The LLM sees the whole conversation each time. There is no lost context between messages. Adding more structured calls (e.g., intake analysis + destination suggestion) does NOT fragment context because all prior turns are always re-sent with each new call. The conversation is one long thread in every call.

### Structured output strategy (carry over the hardened v3 model)
- Keep `AiTripIntakeOrchestrator` on the compact strict schema already proven out in the current branch: `ack_key`, `profile_patch`, `resolved_fields`, `missing_fields`, `next_action`, `next_action_reason`, and flat question fields.
- Keep the acknowledgment short and app-rendered from exactly 4 allowed `ack_key` values: `got_it`, `sounds_good`, `understood`, `perfect`.
- Keep destination recommendations as a second structured call only when `next_action == SUGGEST_DESTINATIONS`.
- Do not grow the new-trip intake schema into a universal schema. Tool routing, existing-trip editing, and group-chat mentions each get their own small schema/orchestrator.

### What "hardcoded" currently means
- **Starter cards** (`AiChatCardCatalog.starterPool`): 12 fixed strings, 8 picked per session.
- **Follow-up card fallback** (`AiChatCardCatalog.nextFollowUpGroup`): hardcoded groups for party, budget, pace, interests, destination style — shown when the LLM-generated follow-up is absent or already asked.
- **Quick reply pills** (`AiTravelerProfileReducer.quickRepliesFor`): 4 fixed options chosen by what's missing in the profile.
- **Destination suggestions** (fresh chat): pulled from `AiCuratedTripCatalog` seeded data, not from the LLM.
- **Place card action labels**: `listOf("Add", "Save", "Swap")` hardcoded in `AiPlaceRecommendationCoordinator`, `actionsEnabled = false` always.

### Reusable UI elements to preserve
- `CurrentTripScreen.kt`, `CurrentTripHeader.kt`, `CurrentTripItineraryContent.kt`, and `CurrentTripDayView.kt` — the current-trip landing and itinerary surfaces. **Reuse for draft trips and existing-trip AI edit previews instead of rebuilding them in chat.**
- `CurrentTripEventDetailsDialog.kt` and `ExpandedEventCard.kt` — detail overlays for events, restaurants, hotels, activities, and any other surfaced place type. **Reuse exactly rather than creating a second AI-only detail sheet.**
- `TripCard` in `HomePage.kt` — hero image card pattern. **Reuse for the AI draft trip card.**
- `GroupChatRow` / `DirectChatRow` in `ChatsPage.kt` — row card pattern reference.

### Shared handler strategy
Goal: keep one user-facing AI entry surface, but route into specialized handlers instead of growing one universal schema.

Routing rules:
- if the session launches with a live `tripId` or current-itinerary context, route to `existing_trip_edit`
- if invocation comes from `@travelcents` inside a chat thread, route to `group_chat_mention`
- otherwise route to `new_trip_intake`
- only fall back to an LLM router when the invocation source is genuinely ambiguous

Handlers:
- `new_trip_intake`: owns preference extraction, next-step questioning, and destination suggestions for net-new planning chats
- `existing_trip_edit`: owns itinerary-aware operations like add, remove, move, replace, update, and explicit day placement against concrete trip entities
- `group_chat_mention`: owns multi-speaker context parsing, consensus detection, and recommendation/clarification inside direct/group chats

Shared building blocks:
- shared `ack_key`-driven short acknowledgments
- shared follow-up card and recommendation-row rendering
- shared `LlmClient` / model config, but separate schemas and orchestrators per handler
- shared `TripPlanActionService` / trip mutation plumbing so AI chat, current trip, and add-to-trip flows do not diverge
